## 链路检查与修复

实际链路为：CPAL 设备采集 → 设备采样率转换为 48 kHz 单声道 → 有界采集队列 → 增益/AEC/降噪/AGC/VAD 或 PTT → 20 ms Opus → 加密 UDP/P2P/SFU → 去重 → 每说话者独立抖动缓冲与 Opus 解码 → 增益/混音/限幅 → 有界播放队列 → 设备采样率转换及播放。

保留正常网络的 96 kbps、48 kHz/fullband 和用户所选降噪。新安装默认 RNNoise，历史配置可能不同。没有通过静默降低正常音质来掩盖卡顿。

| 已确认问题 | v0.6.7 处理 |
| --- | --- |
| 一个缺失的 20 ms 包就可能把缓冲目标从 3 帧增为 6 帧，暂停继续播放 | 孤立丢包使用 Opus FEC/PLC；连续丢包才触发加深缓冲 |
| 重新缓冲把 `started` 清零，迟到的已播放包能把 expected 倒退 | 单独保留已播放边界，重新缓冲也拒绝旧包 |
| 短 PTT/VAD 语句或尾部剩余包不足预填数量，可能永远不播放 | 同时按播放时钟限制等待，不依赖未来一定有新包 |
| 缓冲耗尽后每来一个包就马上播放，长期没有恢复安全余量 | 恢复时重新建立预填，沿用有界等待并保持时间戳连续性 |
| `decode_fec` 返回成功就被计为 FEC 成功，CELT/无冗余时其实可能只是 PLC | 检查本协议 mono/单帧/20 ms Opus 的 LBRR 标志，并跟踪前一解码模式；不能确认的恢复计入 PLC |
| 累计最大连续丢包被当成当前窗口的真实连续丢包 | 按实际解码缺帧维护并取走当前窗口的 burst/max-run |
| backlog resync 保留计数却又累计一次，重复计算历史丢包 | 仅在替换整个 jitter 实例时归档计数；resync 不重复累加，late 计数跨 talk spurt 保留 |
| 多听众共用一个质量状态，每份健康报告可能覆盖弱网听众 | 聚合各听众最新报告，按最差有效报告适配；3 秒过期，新报告替换旧报告，断开清空 |
| 用户容易把内部 48 kHz 误认为设备实际支持相同音质 | 诊断页在协商采样率低于 32 kHz 时显示具体设备音质提示 |

FEC 判断依据：[Opus 解码 API](https://www.opus-codec.org/docs/html_api/group__opusdecoder.html)、[WebRTC 的 LBRR 检查](https://webrtc.googlesource.com/src/+/refs/heads/main/modules/audio_coding/codecs/opus/opus_interface.cc)、已锁定的本地 libopus `opus_decoder.c`。Opus 明确说明：请求 FEC 但没有冗余时按丢包补偿解码；解码成功不是已恢复原音频的证明。当前冗余检测有意只确认本应用实际发送的单声道 20 ms 单帧格式。

## 3 Mbps 的容量边界

以 96 kbps Opus、每秒 50 包、26 B 应用头 + 16 B 认证标签 + 28 B IPv4/UDP 头估算，每条单向转发约 **124 kbps**。全员同时说话的 SFU 出口约为 `人数 × (人数 − 1) × 124 kbps`。

| 全员同时说话 | 估计出口 |
| --- | --- |
| 4 人 | 1.49 Mbps |
| 5 人 | 2.48 Mbps |
| 6 人 | 3.72 Mbps |

这些是预算估算，不是云带宽实测；没有包含 VBR 瞬时峰值、探测/控制流量或其他服务。5 人需要保留余量，6 人全 SFU/96k 已超过 3 Mbps。若经常 5–6 人全员同时发言，房间 64 kbps（quality_7）时 5 人估计为 1.84 Mbps，或增加服务器出口带宽；不需要因本次日志而升级 CPU/RAM。P2P 可以降低服务器转发，但依赖每个人的 NAT 与上行稳定性，不能保证每次可用。

## 安装后的真实设备验收

1. 所有人安装 v0.6.7。保持原房间，先用原来常用的降噪、增益和音量，4–5 人交替说话及同时说话各数分钟。
2. 蓝牙用户对比“蓝牙耳机麦克风”与“独立麦克风 + 耳机播放”或已有有线设备。记录诊断页实际输入/输出采样率。Windows 经典蓝牙 HFP 会降低播放/采集带宽；Windows 软件看到较高的采样率也可能经过系统重采样，不能单凭 48 kHz 排除 HFP。[微软说明](https://learn.microsoft.com/en-us/windows-hardware/drivers/bluetooth/bluetooth-classic-audio)
3. 用已有麦克风测试对比原始/处理后声音；若本地处理后已有电音，而网络诊断正常，继续针对该设备与降噪模式处理，不把它归为服务器问题。
4. 保持一人连续说话，在听众侧分别关闭和开启平常实际使用的 VPN/加速器，记录恢复间隔；操作系统完全断网的区间无法由缓冲消除。
5. 一旦听到问题，立即从说话者和听众两边导出“语音诊断”脱敏报告，并记录时间、房间、是否同时说话。重点对比 PLC、FEC、播放欠载、采集覆盖、DSP 超时与实际设备采样率。
