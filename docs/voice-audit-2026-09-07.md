# 语音优先审查与修复 — 2026-09-07

基线：`17b6986`，工作区版本 `0.6.8`。初始审查与修复在本地完成，随后完成服务端部署；私人部署记录已在开源整理时移除。当时客户端尚未打包更新。

目标是避免本地降噪、P2P 维护、服务端拥塞拖慢通话。检查覆盖 CPAL 采集/播放、重采样、DSP、Opus、Jitter/FEC/PLC、混音、音频线程调度、加密 P2P/SFU、Go 转发队列、聊天落盘锁及桌面状态桥接。没有进行 Windows 真机、真实耳机听感或 TeamSpeak 同场对照，不能据此宣称性能等同 TeamSpeak。

## 已确认并修复

| 优先级 | 原行为与影响 | 本次处理 |
| --- | --- | --- |
| P1 | DeepFilterNet 的结果已经有 40 ms 管线预算，但迟到后还可同步等待 20 ms；该线程也负责接收混音，因而本地降噪超时会影响别人语音的播放 | 只取已就绪结果，保留精确序号匹配、迟到帧丢弃、静音替代及后续帧恢复，不再借用一个播放周期等待模型 |
| P1 | 切换降噪时，旧 DeepFilterNet 的析构会在音频线程 `join` 正在推理的线程 | 关闭双向通道并分离线程；推理线程在当前推理或下一待处理帧发送失败后自行退出、释放模型，音频线程不等待 |
| P1 | 服务端 writer 队列满时，阻塞所有命中该队列的媒体 worker | 入队改为非阻塞；容量不足时丢弃当前批次并计数，避免阻塞向上游扩散 |
| P1 | 只检查 worker 排队时间，不检查 writer 排队时间；拥塞恢复后仍可能发送旧语音 | 从接收时刻起携带音频有效期限，沿用 `MaxQueueDelay`（默认 40 ms），发送前和逐包发送时丢弃过期语音，并设置 UDP 写截止时间 |
| P2 | P2P 密钥准备/加密等待接收线程持有的共享锁 | 改为 `try_lock`；发送侧遇到忙状态时使用现有 SFU 兜底，继续保留加密与混合路径去重 |

正常路径保持 48 kHz、20 ms 帧、默认 96 kbps；未调整用户的降噪模式或码率策略。超负载时 DeepFilterNet 迟到帧仍采用原有静音替代，不过现在严格遵守管线期限，因此弱 CPU 上应关注发送方的 DSP 错误。选择的是保障接收播放截止时间，而非承诺模型超时后还能恢复原音频。切换期间旧模型内存可能短暂保留到推理线程退出，没有新增模型缓存。

新增指标（按出口 datagram 计数）：

- `edenvoice_media_writer_queue_drops_total`：发送队列满导致的丢弃。
- `edenvoice_media_writer_stale_drops_total`：进入 writer 后过期的语音丢弃。

`WriterBackpressureEvents` 现在表示入队被拒绝的批次数；`WriterWaitMaxMicros` 表示非阻塞入队操作耗时，包含线程被调度暂停的时间，不再表示等待空位。日志同步包含新计数。

## 验证与实际结果

环境：本机 macOS 26.4.1，Rust debug 测试、mise Go 1.23。最初沙箱禁止 TCP/UDP/Unix 套接字导致的失败已在允许本机套接字的环境重跑；未把这些权限错误算作程序缺陷。

- Go `go test -race ./...`、`go vet ./...` 通过。
- 客户端最终 `cargo test --lib --offline`：237 通过，1 个五分钟模拟测试默认忽略（已单独运行）；桌面桥接 `cargo test --lib --offline`：19 通过。
- 前端 `npm run build` 通过。
- 修改过的 Rust 文件格式检查、`git diff --check` 通过。`cargo clippy --lib --offline -- -D warnings` 未通过：未修改的 `client/src/application.rs:1412`、`:1420` 存在两处 `collapsible_match` 风格告警；未将此检查描述为通过，未扩大语音修复范围去改写归档/观影分支。
- 新增/增强回归覆盖：满 writer 队列不阻塞；过期音频丢弃后新音频及 probe 正常发送；加密 P2P 锁被持有时有界返回并发往 SFU；连续模型结果缺失不累计 20 ms 等待且能跳过迟到结果恢复；切换模型不等待未完成推理，关闭通道后线程退出。
- 五路真实 Opus 编解码 + Jitter + 混音，五分钟逻辑时间（15,000 个周期）：单独运行时 **0 次 20 ms 超时，峰值 4.826583 ms，最大 jitter 深度 3 帧，0 解码错误**。这不包含 CPAL、降噪、真实网络或 GUI，是处理管线测试，不是端到端延迟。
- 同一测试与编译/大规模转发并发运行时，观测到 **5 次超时，峰值 34.27575 ms**，但没有连续 3 帧超时或缓冲增长。保留该结果，不能以空载通过推出任意游戏/系统负载下无卡顿。

服务端单独运行的 30 秒本机加密 UDP 压测：20 房间 × 12 用户，每房 4 个发言者，共 240 用户、80 路输入，每帧 240 B 合成负载（50 fps 时等效 96 kbps）。注入 1% 随机丢包、5% 乱序、最多 30 ms 延迟、周期性 300 ms burst 和 2 秒 blackout。合成 payload 未经音频解码，不能评价听感。

## 达到目标还需验证的边界

1. **服务器出口带宽**：按本协议每包 26 B 头、16 B 认证标签、28 B IPv4/UDP 头以及 96 kbps 音频估算，每条转发约 124 kbps。全员同时说话时，4 人约 1.49 Mbps、5 人约 2.48 Mbps、6 人约 3.72 Mbps，未含 VBR 峰值及其他流量。若实际出口仍为此前记录的 3 Mbps，6 人全 SFU/96k 超过预算；本次没有核验当前部署带宽。代码优化无法消除物理出口瓶颈。
2. **端到端延迟与听感**：当前默认 jitter 目标 3 帧（60 ms），输出队列目标 2 帧（40 ms）；DeepFilterNet 本身另有约 70 ms 管线/模型延迟。这些参数不能直接作为端到端测量相加。低延迟与抗抖动需要真实设备取舍，未盲目降低缓冲或降噪质量。
3. **设备和系统调度**：Windows 麦克风/耳机、设备拔插、蓝牙、游戏高 CPU/GPU 负载、后台窗口和睡眠恢复都未在本次实机验收。本地代码测试不能验证驱动回调延迟或无线耳机音质。
4. **规模及长期性能**：SFU 每包仍遍历在线 sessions，桌面约每 33 ms 构造/比较状态快照；这些是进一步扩展规模或降低闲时 CPU 的优化候选。现有结果不足以认定它们是小房间卡顿根因。没有 2–8 小时内存曲线；后续已补充 Linux 服务器批量发送实测，见部署记录。
5. **同条件 TeamSpeak 对照**：用同一服务器出口、同一批客户端/耳机及同一网络，分别测 1 人、4–5 人同时说话，记录端到端 p50/p95 延迟、爆音/断音次数、播放欠载、DSP 超时、CPU/RSS 和出口带宽。比较静音、交替说话、同时说话、游戏负载和网络切换；达到共同验收阈值后才能声称体验相当。

聊天落盘已经在释放媒体使用的全局状态锁后执行；CPAL 回调使用非阻塞音频队列；每个远端独立 decoder/jitter，已有 FEC/PLC、去重和设备恢复回归。本次保留这些设计。主要收益是减少可确认的跨线程等待与拥塞累积，不以未测数据证明音质等同其他客户端。
