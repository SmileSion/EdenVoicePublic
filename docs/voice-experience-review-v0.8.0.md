# V0.8.0 通话体验复核

基线：ab1286f。范围为默认自动码率、自动网络、语音活动输入；另检查 PTT 和降噪切换。重点排除正常网络、轻微抖动、一般系统负载变化下的软件断音，不把用户严重网络丢包列为本轮缺陷。

## 已确认的采集侧问题

1. **P1：降噪切换时门限判断与最终波形不一致。** `client/src/audio/capture.rs` 在新处理器输出上计算 analysis，随后才与旧处理器波形交叉渐变。若新处理器尚输出静音、旧处理器仍有语音，最终波形有声但 voice_active 为 false，音频 worker 会丢弃这帧。临时用例使用同一处理器分析和交叉渐变函数，确认最终 RMS > 0.05 但发送条件仍为 false。应对最终波形进行发送判断，保留切换期间语音活动连续性，并覆盖不同算法延迟。
2. **P2：轻声起音没有回补。** 当前能量 VAD 阈值为 0.004，release 保护句尾，但未保留发送前的起音帧。临时输入前三帧幅度 0.003、第四帧 0.03，只有第四帧进入发送条件，前 60 ms 被丢弃。该测试证明门限行为，不证明任意真实声母一定被吞。建议增加有界起音预留、开门时补齐，并在安静语音/键盘噪声录音上校准阈值。

## 代码确认、尚需时序或设备复现的风险

- **P2：PTT 松键尾字。** 捕获帧不携带按键时序，发送时使用当前按键状态。若松键前采集的帧仍在 DSP/队列中，松键后完成处理会被丢弃；只影响按键说话，不影响默认 VAD。应记录采集期 PTT 区间，保留已授权采集的尾帧，同时保持静音操作即时生效。
- **P2：CPU 压力下只有提示，缺少自动降级。** DSP 持续超时会生成警告，采集/处理结果过期或队列满会丢帧；没有自动切到较轻处理模式。默认 RNNoise 本轮未复现超时，DeepFilterNet 或游戏高负载场景需设备测试。
- **P2：自动路由选择合格路径而非最优路径。** 房间全员 P2P 合格后允许迁移，尚未要求它比 SFU 的实际媒体质量更好。前几轮已指出，本次未修改。应在收益明确时切换，并考虑多人发送的上行成本。

## 检查及验证证据

- 复核采集回调、DSP 工作线程、发送门限、Opus、收包及防重放、SFU/P2P 保护、播放缓冲及时间伸缩、混音、输出回调、设备恢复、控制反馈和 SFU 拼包/转发衔接。
- 本轮执行五路 Opus 编解码/混音的五分钟模拟：15,000 个混音周期、75,000 个输入帧，20 ms deadline misses=0，单轮峰值 8.130333 ms，最大每路缓冲深度 3 帧。实际运行约 20.91 秒，为本机 debug 离线模拟，不包含网络、真实设备回调、RNNoise 或操作系统持续高负载。
- 两个临时采集门限复现用例通过，之后恢复代码。日志：`/tmp/edenvoice-final-review-repros.log`；长时模拟日志：`/tmp/edenvoice-audit-long.log`。
- 上轮在同一已提交基线上已验证客户端 276 项测试、严格 Clippy、前端构建及服务端 protocol/voice/serverstate/control/voice-server race 检查；不能用这些测试替代真实设备听感验收。

这些资料没有提供本项目可直接套用的同条件延迟/断音测试结果，不能据此宣称已经达到或超过它们。

应固定对标客户端版本和设置，在相同设备、同一网络条件下验证：2/6 人通话，正常及轻度抖动，游戏负载，持续数小时，轻声起音/短句/抢话，降噪热切换，PTT 松键，有线/USB/蓝牙设备与热插拔。记录口到耳延迟分位数、连续断音时长、欠载、采集丢帧、切路中断和盲听结果。严重公网丢包可排除，但系统调度和设备适配不能归类为网络免责。
