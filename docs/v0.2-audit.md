# Eden Voice V0.2 Audit

Date: 2026-08-19

This audit treats `Eden_Voice_V0.2_Daily_Driver_Foundation_Prompt_v4_consistent.md`
as the V0.2 product and acceptance baseline. Where earlier and later sections differ,
the final consistency section and revised P0 list take precedence.

## Baseline safety

- The repository started clean at commit `76516de feat:v0.1_base`.
- V0.1 is committed and recoverable. No reset, clean, or destructive migration is

- A local CodeGraph index was created for dependency and call-path analysis.

## Current architecture

### Go server

The server is already appropriately small for V0.2:

```text
TCP control listener -> per-connection dispatcher -> shared authoritative State
UDP socket -> packet validation -> session/channel lookup -> unchanged datagram relay
```

`serverstate.State` owns channels, sessions, heartbeat time, mute/deafen presence,
and registered UDP endpoints behind an `RWMutex`. Control connections use one
goroutine each. The UDP relay uses one read loop and does not decode Opus or create a
goroutine per packet. Broadcast copies senders while holding the state lock, then
performs writes after releasing it.

The relay validates the packet format, session ID, and exact observed source address.
It forwards only to registered, non-deafened peers in the sender's authoritative
channel. This design should remain unchanged for V0.2. Per-user gain, local mute,
input/output gain, VAD/PTT gating, AEC, AGC, and noise suppression are client-local
and require no server protocol additions.

### Rust client

The working voice path is:

```text
egui EdenVoiceApp
  -> ControlHandle command channel
  -> TCP/NDJSON control thread

CPAL capture callback
  -> bounded 20 ms frame queue
  -> voice worker
  -> Opus encoder
  -> VoiceTransport / RelayTransport
  -> UDP

UDP receiver thread
  -> bounded packet queue
  -> per-peer jitter buffer and Opus decoder/PLC
  -> mixer
  -> bounded playback queue
  -> CPAL output callback
```

The client already has valuable core boundaries:

- `VoiceTransport` hides relay transport details.
- `RemotePeer` owns one decoder and jitter buffer per remote session.
- Opus is isolated in `codec`.
- Protocol encoding is independent of egui and CPAL.
- CPAL callbacks use bounded non-blocking channels and fixed 960-sample frames.
- TCP control, UDP receive, Opus, peer management, and mixing run off the audio
  callbacks.

The main architectural debt is `client/src/app.rs`. The egui application currently
parses protocol envelopes, mutates network-derived state, controls audio lifecycle,
sends control commands, persists settings, enumerates devices, and renders every
screen. The underlying core is not coupled to egui, but the application boundary is
implicit rather than enforced.

### Threading and real-time behavior

Current threads are the UI thread, one TCP control thread, one audio-controller
thread, one voice worker, a CPAL input callback, a CPAL output callback, and one UDP
receiver thread while audio is active.

Good properties to preserve:

- CPAL callbacks perform sample conversion, channel fold/duplication, fixed-frame
  assembly, gain/clamp, and non-blocking queue operations only.
- Network I/O, Opus, JSON, logging, device enumeration, and disk I/O stay outside
  callbacks.
- Audio and UDP queues are bounded.
- No unsafe code or blocking mutex is used in an audio callback.

Risks to address:

- The capture callback replaces a fixed frame after every send. This is a small
  fixed-size stack copy, not an unbounded allocation, but DSP should remain in the
  worker rather than move into the callback.
- The voice worker allocates `Vec`s for decoded frames and frame references every
  20 ms. It is not the device callback, but preallocated scratch storage is preferable
  before adding expensive DSP.
- Voice packet encode/decode allocates payload vectors per packet.
- A fixed three-frame jitter prefill is simple and tested but not adaptive.
- Input gain and output volume are captured when streams start. Changing either
  currently rebuilds the whole local audio engine and UDP transport.
- A selected device failure produces an error but there is no device-lost event,
  retry, or automatic fallback state machine.
- The output callback substitutes silence on queue underrun but underruns and
  overruns are not counted.

## Existing capability inventory

V0.1 already provides:

  mute/deafen state, heartbeat, RTT, reconnect backoff, UDP re-registration, and

- Custom UDP registration and relay, Opus at 48 kHz mono with 960-sample/20 ms

## Boundaries to refactor

### Phase 1: application boundary

Introduce explicit `AppCommand`, `AppEvent`, `Application`, and `Dispatcher` types.
The egui layer may hold transient presentation state, but it must only read an
application view and dispatch commands. It must not import control protocol envelopes,
`ControlHandle`, `AudioController`, sockets, CPAL devices, codecs, jitter, or mixer.

The first extraction should preserve behavior exactly:

```text
egui -> AppCommand -> Application/Dispatcher -> control and audio adapters
control/audio event -> AppEvent -> Application -> AppState -> egui
```

Do not combine this extraction with a protocol, audio, or GUI framework migration.

### Phase 2: UI/design system

Continue with egui. It already supports Windows, macOS, Linux, custom visuals,
reusable widgets, immediate-mode animation driven by stable IDs/time, HiDPI, and low
idle repaint rates. The current UI underuses these capabilities; that is not a
framework limitation.

Split UI code into theme tokens and focused views/components. Provide System, Light,
and Dark palettes; semantic colors; spacing, radius, typography, and animation
durations; then rebuild connection, channel tree, member rows, controls, settings,
and diagnostics. Avoid an all-card layout and preserve native platform expectations.

### Phase 3 onward: audio/DSP boundary

Create a capture processing pipeline whose engines are replaceable and whose default
implementations are pass-through. Keep the network frame at 48 kHz mono/20 ms and
adapt internally to 10 ms or 480-sample processors.

Recommended boundary:

```text
CaptureProcessor
  -> manual input gain
  -> EchoCanceller (capture + render reference)
  -> NoiseSuppressor (exactly one engine)
  -> AutomaticGainController
  -> LevelAnalyzer
  -> VoiceActivityDetector
  -> input gate

decoded peer -> per-user gain/local mute -> mixer/limiter
  -> master gain -> render-reference queue -> output
```

Heavy engine creation and model loading belongs to a DSP manager/worker. An initialized
processor is swapped only at a frame boundary while the previous processor remains
active. DeepFilterNet must not load, allocate a permanent worker, or retain model
memory until selected.

## DSP dependency research

Sonora 0.2.0 is now integrated as the provisional production foundation for Standard
NS/AEC/AGC. Cross-platform release builds, latency, and real-device quality remain
release gates. Model redistribution remains a separate gate for learned engines.

### AEC, Standard NS, and AGC

Primary candidate: WebRTC Audio Processing Module (APM), exposed through a maintained
Rust wrapper or a verified equivalent. APM natively groups AEC, traditional noise
suppression, AGC, and VAD and expects render/capture processing with delay handling.

Two candidates were evaluated at the packaging/API level:

1. `tonarino/webrtc-audio-processing`: established BSD-3-Clause Rust bindings around
   the PulseAudio extraction of WebRTC APM. It supports a bundled build, but adds a
   C++ toolchain plus pkg-config, Meson, Ninja, and wrapper versioning that is not
   conventional semver.
2. `dignifiedquire/sonora`: BSD-3-Clause, pure-Rust port of WebRTC M145 AEC3, noise
   suppression, and AGC2 with runtime SIMD and CI claims for macOS arm64, Windows
   x86_64, and Linux x86_64. It removes the C++ packaging burden and is attractive,
   but is newer and needs Eden Voice real-device AEC validation before release.

Current decision: use Sonora as the foundation and retain the C++ wrapper as a
fallback candidate if quality testing fails. The integrated adapter splits 960-sample
frames into two preallocated 480-sample chunks and supports live processor replacement
without rebuilding the voice transport. Verify render/capture delay behavior, run a
speaker-to-microphone test, and measure release DSP time. Do not hand-roll AEC.

### RNNoise

Upstream Xiph RNNoise is BSD-3-Clause, CPU-only, designed for 48 kHz mono, and processes
480-sample/10 ms frames. It fits the existing 960-sample network frame by splitting
each frame in two. Upstream recommends runtime CPU dispatch rather than forcing AVX2.

Selected implementation: `nnnoiseless 0.5.2` with default features disabled. It is a
BSD-3-Clause pure-Rust port, exposes a reusable `Send + Sync` denoiser state, and
processes the two native 480-sample blocks without per-frame heap allocation. Its
built-in 87,521-byte model is pinned by SHA-256 in `docs/audio-processing.md` and its
binary redistribution notice is in `THIRD_PARTY_NOTICES.md`. RNNoise has no general
user strength setting in its core frame API, so its capability reports Automatic.

### DeepFilterNet

The official DeepFilterNet repository includes Rust inference (`libDF`/`deep-filter`),
pretrained models, a real-time LADSPA path, 48 kHz support, and states support for
Linux, macOS, and Windows. It also has STFT/model lookahead latency and materially
higher CPU/RAM/model-size cost than RNNoise.

Before bundling, pin a specific model and separately verify source-code and weight
redistribution terms. Prototype streaming inference in release mode, record model
size, resident memory, algorithmic latency, average/peak frame time, and deadline
misses, and test unloading. If the official Rust crates cannot be embedded cleanly,
the feature must remain unavailable with a clear reason rather than being simulated.

Research sources:

- WebRTC APM overview: https://webrtc.googlesource.com/src/+/main/modules/audio_processing/g3doc/audio_processing_module.md
- WebRTC Rust wrapper: https://github.com/tonarino/webrtc-audio-processing
- Sonora: https://github.com/dignifiedquire/sonora
- RNNoise: https://github.com/xiph/rnnoise
- DeepFilterNet: https://github.com/Rikorose/DeepFilterNet

## GUI and cross-platform risks

- egui/eframe and CPAL support all three target desktop systems, but actual device
  names, default-device behavior, permission prompts, and hot-plug signals differ.
- macOS microphone permission metadata and signing/notarization are not yet present.
- Windows global hotkeys and audio behavior require a backend adapter and packaging
  validation; Linux global hotkeys vary between X11 and Wayland and may require portal
  support. A single desktop-specific implementation must not leak into application
  state.
- Hardware sample-rate negotiation is covered with synthetic CPAL ranges and the
  resampler is covered with deterministic unit tests; physical Bluetooth headsets
  still need release validation on each supported operating system.
- There is intentionally no hosted CI configuration. Rust and Go checks must be run
  manually on macOS, Windows, and Linux with native DSP prerequisites installed.

## Technical debt and correctness risks

- `app.rs` is a large mixed UI/application module.
- Deafen currently forces server mute, but turning deafen off does not encode a
  separate remembered manual-mute intent. V0.2 must preserve manual mute semantics.
- Reconnect emits `Error` between reconnect states, and the UI drops back to the
  connection screen instead of keeping a stable main-window reconnect presentation.
- Restarting audio rebuilds the UDP transport; runtime gain/device changes should
  rebuild only the minimum local pipeline and preserve the voice/control session.
- Per-peer gain/local mute do not exist, and remote decoded frames lose the peer ID
  before the mixer, so gain must be applied while iterating peers.
- The mixer now uses a zero-lookahead soft limiter after per-user gain and master
  volume. Its quality still needs multi-speaker, real-device acceptance at >100% gain.
- Local speaking follows the final VAD/PTT send gate; remote speaking follows received
  audio packets. Attack/release behavior still needs real keyboard/game acceptance.
- Diagnostics now include packet reorder/loss, aggregate jitter depth, input RMS/peak,
  output RMS, queue underrun/overrun, active processing, DSP timing, and deadline
  misses. Long-run measurement remains a release task.
- Settings writes are direct and non-atomic. Corrupt/partial JSON silently falls back
  to defaults. A temporary-file/rename strategy should be considered.

## Implementation plan

1. Extract the application boundary and add pure command/event/state tests while
   keeping V0.1 behavior unchanged.
2. Add the design system, themes, focused UI modules, and settings/diagnostics
   navigation.
3. Introduce DSP/gain/VAD interfaces with no-op engines, metrics, and tests.
4. Add input gating, per-user gain/local mute, master gain, clipping protection,
   meter behavior, and persistence.
5. Prototype and select APM implementation; integrate render reference, AEC,
   Standard NS, AGC, and capability-driven strength. **Foundation integrated with
   Sonora 0.2.0; real-device and cross-platform acceptance pending.**
6. Integrate RNNoise with two 480-sample blocks per network frame and release metrics.
   **Engine, frame adaptation, model/license record, live switching, and metrics are
   implemented; cross-platform release and real-noise acceptance remain pending.**
7. Prototype, license-check, integrate, and lazy-load a pinned DeepFilterNet model.
   **Official DFN3 v0.5.6 Tract inference, pinned model/hash/license record, dedicated
   loader and inference threads, request coalescing, generation cancellation,
   frame-boundary swap, timing, failure rollback, and deterministic worker join on
   unload are implemented, and the isolated release probe records a +63.81 MiB peak
   RSS delta versus Off. Real-noise, long-session memory trend, Windows, and Linux
   acceptance remain pending.**
8. Add safe background engine switching, failure rollback, diagnostics, and tests.
   **Controller-thread construction, frame-boundary swap, truthful fallback, and
   timing diagnostics are implemented for all four modes.**
9. Add runtime device switching/loss fallback without rebuilding the network session.
   **Implemented at the CPAL stream boundary with rollback and default-device
   recovery; real unplug/replug acceptance remains pending.**
10. Add Voice Activity and platform-adapted global PTT with explicit permission/error
    states.
11. Add mic/output tests, reconnect polish, performance baselines, audio-processing
    documentation, and real-device acceptance runs. **The code, local automated
    verification, and documentation are implemented; manual cross-platform packages
    and real-device acceptance runs remain.**

## Phase 0 exit decision

Phase 0 was completed before implementation. V0.1 remains protected and green; egui
and the existing voice core were retained, and the application/UI boundary was
extracted before DSP integration. Sonora, nnnoiseless, and the pinned DeepFilterNet
Tract backend now form the processing foundation. AEC/denoise listening quality,
cross-platform release artifacts, real device-loss behavior, and long-run CPU/RAM
still require measured acceptance rather than assumptions.
