# v0.6.3 语音诊断与持续压测

## 客户端诊断

设置页的“语音诊断”展示媒体/控制 RTT、Jitter、有效音频丢包率、实际 P2P/SFU/Relay 链路、Opus 码率、FEC/PLC、Jitter 缓冲深度/延迟/欠载、设备播放欠载和实际输入输出设备/采样率。

“导出脱敏报告”生成 `edenvoice.voice-diagnostics.v1` JSON。报告不包含昵称、聊天、服务器明文地址、Client ID 或设备名称；需要关联的标识经 SHA-256 后仅保留前 8 字节。

## 服务端指标

默认监听 `127.0.0.1:9100`：

- `/healthz`：进程存活检查；
- `/metrics`：Prometheus text format。

指标覆盖全局收发包/字节、认证与写失败、worker/writer 队列深度/高水位/等待/丢弃/背压，以及进程 CPU seconds、内存和 goroutine。每个活跃或历史有媒体的房间按 `channel_id` 输出人数、包计数和平均包速率。

生产建议保持 loopback 监听，由本机 Prometheus 拉取；若修改为公网地址，必须配合防火墙或带认证的反向代理。

## 持续压测

`voice-load` 在本机建立真实 UDP socket 和每会话 ChaCha20-Poly1305 密钥，服务端完整执行收包、分片 worker 解密、按接收者重加密和 writer 批量发送。客户端侧验证解密结果，并支持：

- 独立随机丢包；
- 额外延迟与乱序；
- 周期性突发丢包；
- 周期性网络中断。

快速验证可使用 `-duration 30s`；常规 soak gate 为 2 小时，发布前 gate 为 8 小时。成功结果必须满足：

- `status=ok`；
- 客户端解密错误为 0；
- 服务端认证和写失败为 0；
- 没有非预期的 worker 队列丢弃或过期帧；
- 指标中 20 个房间相互隔离，收发包速率与说话人数匹配。

项目不再通过 GitHub Actions 定时运行压测。在 `server/` 目录中手动运行，并将结果保存在本地：

```bash
go run ./cmd/voice-load \
  -rooms 20 -users-per-room 12 -talkers-per-room 4 \
  -duration 2h -report-interval 30s \
  > /tmp/edenvoice-voice-load-result.json
```

需要验证同一进程连续运行 8 小时时，将时长改为 `-duration 8h`。弱网注入参数可按上文配置；没有自动上传测试结果的流程。
