# Room social v1

The existing authenticated TLS control connection carries `room_social_request` and `room_social_event` envelopes. Welcome advertises `room_social_v1`; `room_images_v1` is additionally advertised when durable image storage is available. Clients hide or disable unsupported controls. No new port or media messages are used.

Requests contain `request_id` (1–64 ASCII characters), `channel_id` (current nonzero room), and `action`. All actions require authenticated current room membership. Changing room invalidates outstanding uploads, including leaving and returning to the same room. Session identity always comes from the connection.

| action | Additional request fields | Successful event kind and fields |
| --- | --- | --- |
| status | none | status: `away:[{session_id}]` (omitted means empty) |
| away | active: explicit boolean | away: session_id, active (true sets, false clears) |
| reaction | emoji: 👍 ❤️ 😂 🎉 👏 ☕ | reaction: session_id, emoji, expires_at_unix_ms |
| image_begin | bytes, width, height | image_upload: upload_id, offset=0 |
| image_chunk | upload_id, offset, data (standard base64) | image_upload: upload_id, offset=total accepted raw bytes |
| image_commit | upload_id | image_committed: upload_id, image |
| image_cancel | upload_id | image_cancelled: upload_id |
| image_get | reference, offset | image_data: reference, offset=request offset, data, eof, image |

Events contain `kind`, `channel_id`, and the originating `request_id` if solicited. Away/reaction success is broadcast only to current room members including the requester; only the requester receives request_id, preventing unrelated pending RPCs from colliding. Other replies are private. Unsolicited away-clear events omit request_id. Errors use kind `error`, code, message and optional retry_after_ms. `busy` means retry the same operation after retry_after_ms; no bytes were accepted. Reaction cooldown errors also use `busy`. Status never includes old reactions. Images produce a normal `text_message` with text `"[图片]"` and optional `image:{reference,mime:"image/jpeg",width,height,bytes}`. The same metadata is retained in chat history; no base64 payload is stored in chat, global snapshots or archive events.

Images must be JPEG, at most 256 KiB, with positive dimensions, longest edge at most 1600 and at most 2,560,000 pixels. The server decodes both header and pixels before accepting. Each upload/download chunk contains at most 8192 raw bytes. Downloads are request-driven (one chunk per request); clients keep at most one request in flight and discard responses after room changes. A server-wide 64 KiB/s wire budget with a small bounded burst and individual session limits protect the control queue. Busy responses never sleep while holding a state lock.

Away is session-only and has no timeout. Setting active=true atomically sets the session muted and broadcasts the ordinary user_state_changed event to all clients, then the room-scoped social away event to subscribed members. Calling set_mute with enabled=false atomically clears away and emits active=false; this covers microphone buttons, shortcuts and tray controls using that command. Deafen-only changes do not clear away. Explicit active=false, room changes and disconnect clear presence without automatically opening the microphone. Requests must provide an explicit active boolean; the former minutes/until fields are not supported. Reactions live 2500 ms, allow one per person per 2 seconds, and have a room-wide bound. Uploads expire after 60 seconds, allow one per session and at most 1 MiB reserved server memory. Stored image files expire after 30 days and total image storage is capped at 64 MiB; a history item may therefore show image unavailable. Persistence failure never broadcasts an image message. Old clients continue receiving regular message envelopes with ignorable optional metadata.

Social broadcasts go only to sessions that have sent a valid room_social_request (normally status after joining). This opt-in prevents unknown envelope types from reaching older clients.

Resource bounds: upload/download each use a global 64 KiB/s encoded-byte budget (16 KiB burst) and a 32 KiB/s session budget. At most 8 uploads (1 MiB total reserved), 2 disk/decode jobs globally, and 1 such job per session can be active. Slots are reserved before spawning background jobs; there is no waiting job queue. JPEG validation, attachment I/O and image chat persistence run outside the control read loop and social/voice state locks, so the same TLS connection can still process ping, mute, leave and cancel during slow storage. Busy commit preserves the upload for retry. Reservations remain held until the actual task finishes even after cancellation or disconnect. Every final private result, including errors, rechecks membership and room generation. Reaction delivery allows 4 per second per room with a 6-event burst; each session accepts at most 20 social requests per second. Storage also limits image count to 4096.

Cancelling while attachment persistence is pending immediately ends the original commit RPC with `upload_missing` and acknowledges the cancel RPC with `image_cancelled`. The background task then discards the persisted attachment without publishing it. Once a commit has entered chat publication, cancel returns `busy`; it never reports a published image as cancelled. Leaving a room or disconnecting invalidates outstanding private results, including leaving and rejoining the same room.

Error codes: `invalid_request`, `forbidden`, `busy`, `secure_mode_required`, `unavailable`, `storage_full`, `invalid_image`, `upload_exists`, `upload_missing`, `invalid_chunk`, `incomplete_image`, `message_failed`, `image_missing`. Filesystem failure details stay on the server; responses never include storage paths. `storage_full` requires freeing capacity or retention cleanup, while `unavailable` indicates a storage/IO failure. Both preserve the client preview; restart the upload when retrying a failed commit.

Screen sharing privacy state is carried by the existing `screen_share_request` / `screen_share_state` envelopes. `action:"pause"` requires `share_id`, current `channel_id`, and an explicit `paused` boolean. Only the current publisher may change it. State/status/subscribe responses include `paused` (false for a fresh or stopped share). Only changes broadcast a new room state. The publisher must replace outgoing video with safe placeholder frames and silence outgoing share audio before announcing pause; the server continues forwarding media so older viewers receive the replacement instead of freezing the last private frame. Screen privacy pause does not change voice mute or away presence.
