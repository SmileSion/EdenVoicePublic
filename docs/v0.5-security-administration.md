# V0.5 Security, Identity, and Administration

V0.5 makes secure mode the production default. The control listener uses TLS 1.3. A persistent Ed25519 server identity signs the TLS certificate and is pinned by endpoint after an explicit first-connection fingerprint confirmation. Clients persist a separate Ed25519 identity; `ClientID` is the base64url SHA-256 digest of its public key and is authenticated with a fresh, handshake-bound challenge signature.

Each connection also creates ephemeral X25519 keys. HKDF-SHA256 derives direction-separated client/server media keys and nonce prefixes. Long-term identity keys never encrypt media. Reconnection creates a new ephemeral context.

UDP voice protocol v2 adds a two-byte `key_epoch` to the existing header. The complete 26-byte header is AEAD additional data and the Opus payload is protected with ChaCha20-Poly1305. Nonces combine a session nonce prefix, epoch, and sequence; per-stream subkeys prevent nonce reuse when an SFU sends multiple speakers through one receiver session. A 64-packet sliding window accepts bounded reordering and rejects duplicates and stale packets. The SFU authenticates and decrypts before checking the authoritative server-mute state, then encrypts separately for each recipient. Authentication failures and invalid packet/source/registration/write events are counters; diagnostic warnings are sampled to at most three per category per ten-second window and report the suppressed count on the next window.

P2P candidates carry only an authenticated ephemeral public key, never a private key or long-term media key. Peers derive separate directional pairwise media contexts. Direct media is used only after the peer key and route are both ready; otherwise the client keeps the SFU path.

Before the media sequence wraps, the client requests a coordinated two-phase rekey. The server prepares the next epoch, waits for the client acknowledgement, and then commits it; both sides retain the previous epoch during the in-flight grace period. Pairwise P2P contexts perform the equivalent deterministic epoch transition at sequence wrap.

Administration state is atomically persisted under `security.data_dir`:

- users, identity public keys, display names, and `MASTER` / `ADMIN` / `USER` roles;
- `CHANNEL_ADMIN` assignments;
- bans, including operator, reason, and optional expiry;
- dynamically created and edited channels.

The server is the authorization boundary. All governance messages pass through the centralized `Authorize(subject, action, resource)` policy. `ADMIN` cannot manage `MASTER`; channel administrators cannot manage server administrators or escape their channel scope. Administrative mute is enforced physically on the SFU ingress path. In P2P mode, a compliant sender keeps capture muted while `admin_muted` is authoritative and compliant receivers suppress that peer; local unmute cannot reopen capture or override receiver suppression. Direct P2P packets do not traverse the server, so a malicious modified client can bypass that client-side enforcement. Operators requiring a server-enforced media boundary must force SFU or remove the client with kick/ban. Channel deletion moves members to a safe fallback and clears channel roles, routing, reports, and subscriptions.

The existing context menus are capability-aware and invoke real server operations for channel creation, editing and deletion, targeted room-network policy, administrative mute, move, kick, ban, unban, and server/channel administrator assignment. Channel create/edit/delete and member mute/channel-kick/server-kick use separate UI flags mapped to their exact server action; one granted action never enables a sibling action. The server-provided channel scope is also checked against the context channel or target user's actual channel before enabling channel-scoped operations, with move requiring both its source and destination to be in scope. Setting CHANNEL_ADMIN derives its ClientID and channel scope from the selected target session, not the operator's current channel, and refuses stale or no-channel targets locally. Session-level moderation carries both the selected `session_id` and its authenticated `client_id`; the server rejects a mismatch and never chooses an arbitrary connection when one identity is online more than once. The UI also preserves `admin_muted` independently from the effective `muted` display state, so a user's own mute never turns the administrator action into a false “unmute” operation. Ban remains identity-level and immediately disconnects every active session for that ClientID. A policy request may target a channel even when the operator is not joined to it; authorization is evaluated against the requested channel and the change is audit logged. MASTER and ADMIN can page through active bans in the client and remove a ban; listing and removal are separately authorized by the server. The UI only hides unavailable actions for convenience; the server reauthorizes every request.

Room-network editing is enabled only when the server grants `network.policy.set`. Capability messages also carry `network_policy_channel_ids`: MASTER and ADMIN receive every channel, while CHANNEL_ADMIN receives only channels within that assignment's scope, even when the administrator is not currently joined to one of them. Creation and deletion refresh this list for online sessions. The dotted capability name and target-channel scope are part of the control-protocol compatibility contract and are asserted by both server and client tests.

Room-network policy belongs to the channel rather than to its current occupants. The administration store persists `auto`, `force_sfu`, or `force_p2p`; ordinary channel edits preserve it, an empty room does not delete it, and startup restores it into routing state. Server snapshots expose each channel's authoritative value, so the context editor initializes from the selected room instead of a client-local default. Joining or reconnecting to a room does not push a stale client-local preference back to the server; only an explicit authorized save changes the policy. Older persisted state and older snapshots that omit the field normalize safely to `auto`.

On a new data directory the server logs a one-time MASTER provisioning token. If no MASTER has claimed it before restart, the token is rotated. Operators can recover an existing identity locally:

```sh
mise exec -- go run ./cmd/voice-server -config config.toml -recover-master-client-id CLIENT_ID
```

Server identity creation, one-time provisioning-token generation, local MASTER recovery,
and legacy-insecure compatibility enablement also emit structured `security audit` JSON
records. The provisioning token itself remains confined to its dedicated one-time console
message and is never duplicated into the audit record.

Security files are created with owner-only permissions. Existing client identity/trust and server identity/administration files inherited with wider modes are tightened to `0600` with `0700` parent directories before they are decoded; failure to protect them aborts loading. Private keys and session secrets are not included in normal logs or debug formatting.
The client also treats an unreadable or malformed server trust store as a hard error; it never falls back to an empty store or silently replaces existing endpoint pins.

On an Apple M5, the 2026-08-25 secure-media regression run measured 0.536–0.567 microseconds for one seal/open pair. The secure SFU benchmark (one decrypt plus five recipient encryptions) measured 1.914–1.916 microseconds per packet, 62.62–62.71 MB/s, and 14 allocations. These figures are a regression baseline rather than a cross-machine performance guarantee; detailed commands and allocation figures are in `docs/performance.md`.
